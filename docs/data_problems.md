# Data problems and decisions — rooftop-PV detection MVP

This document is the consolidated reference for every data problem uncovered while scoping the ML model that predicts whether a household has a rooftop PV system (Energy Data Hackdays 2026, AEW "Energy Fingerprints"). Each row pairs a problem with the decision or workaround we settled on. Numbers are as measured against `store/input_data/` (GIGI: 1,192 rows / 878 unique `GP-Nr`; `Zähler-GP`: 89,910 rows; 42–43 monthly smart-meter exports, ~77 GB).

| Problem | Solution / Decision |
|---|---|
| **① Raw files & formats** | |
| 43 monthly export files, 0.8–3.4 GB each (~77 GB total) — cannot be held in memory together. | Single streaming pass, one file at a time; accumulate per-`(meter, month)` aggregates to a compact feature table rather than retaining raw rows. |
| Non-standard layout: `;` delimiter, `Datum` as `DD.MM.YYYY`, German month-folder names (`Januar 2024`), a doubled `2023/2023/<month>/` path, and a trailing empty 101st column. | Fix all parsing parameters explicitly in `config.py` (separator, date format, column list); hard-code the folder-name map and the `2023/2023/` special case; drop the phantom last column on read. |
| UTF-8 BOM on `HackDays2026 - GIGI.csv` and `Zähler-GP.csv` corrupts the first column name (`﻿GP-Nr`), breaking header matches. | Read these files with a BOM-aware encoding (`utf-8-sig`) / strip the BOM before matching column names. |
| Duplicate export files: flat `2023/`, `2024/` … directories hold the same timestamped exports as the `<year>/<month>/` folders. | Deduplicate by the timestamp embedded in the filename before building the file list; keep one copy per month. (As currently staged the flat copies are already gone.) **Updated:** `2023-03` was never an empty folder — it held a stalled server-side upload, `LG_AIM2Hackerdays_kWh_20260827_084034.csv.tmp.5695`, that was never renamed. Verified complete (1,754,910 rows, all 31 days, both OBIS registers, uniform 101-field lines) and now picked up by `discover_monthly_exports(include_stalled_uploads=True)`. **43 months, not 42**; `KNOWN_MISSING_MONTHS` is empty. |
| The `April 2023` export ships a header row that is **missing the `OBIS-Code` label** (100 names for 100 data fields incl. OBIS) — trusting header names silently shifts every column (OBIS read as `Datum`, date as `PLZ`, …). | Parse the exports **by column position**, never by header name: every row is `MP ID ; OBIS-Code ; Datum ; PLZ ; <96 values>`. Implemented in `stream.py` with `header=0, names=[…]`. |
| The `Oktober 2024` export looks partial/truncated (~31.8k meters vs ~47k in `Juli 2024`). | Keep it and flag it (`is_partial_month` in `meter_month_labelled.csv`); rely on multi-month aggregation. **Correction:** a minimum-valid-days threshold does **not** protect against this — 2024-10 is thin in *meters* (48 of our 413 labelled, vs 195 in 2024-09), each carrying a full 31 days. `MIN_DAYS_PER_MONTH` drops nothing here. The real safeguard is that per-meter means are computed over all available months, so an absent meter contributes nothing rather than a biased value. |
| Python environment lacks `pyarrow`, `xgboost`, `lightgbm`, `duckdb`. | Use scikit-learn (`HistGradientBoostingClassifier`) for modelling; fall back to `.npz` / compressed CSV for on-disk interchange, probed at Step 0. |
| Each meter-day appears as two rows by OBIS code — `1-1:1.29.0*255` = grid import (consumption), `1-1:2.29.0*255` = feed-in/export. | Split the two channels on load; carry the import channel into features and route the export channel to offline use only (see block ④). |
| **② Join chain: linking households to meters** | |
| Only 337 of 878 labelled `GP-Nr` resolve to any meter data through the chain (`MP ID` → `mpid_zähler_mapping` → `Zähler-GP` → GIGI `GP-Nr`). | Verified this is a genuine coverage gap, not an ID-format bug — both sides share the same 6-digit numeric space and the true overlap is 337. Accept the reduced linked set, and pursue silver labels + a better mapping to grow it. |
| Canton mismatch: 829/878 labelled households are in canton AG (AEW's territory); the ~49 in SO/BL/ZH/LU/BE almost never join. | Scope the model to AG; treat the non-AG labels as effectively unusable for supervision. |
| Even within AG, only ~41% (336/829) of labelled households appear in the 89,910-row `Zähler-GP` partner table — the rest are simply absent from the meter-data customer sample. | Accept the small linked cohort for the MVP; note that a more complete `GP → metering-point` mapping (pending user input) would roughly double the training set. |
| 46 of the 337 linked households map to more than one metering point (max 17). | Extract features per `MP ID`, then aggregate meters up to the household (`GP-Nr`) with a consumption-weighted mean; keep `n_meters` as a feature. |
| A household's meter set can include a dedicated PV-production meter (export-only) that would pollute consumption features. | Interim heuristic: flag and exclude export-dominant meters (annual `2.29` ≫ `1.29`, negligible night import) from consumption-feature aggregation; replace with the per-`GP-Nr` pooled-meter dataset the user will provide. |
| Smart-meter rollout: meter count in the exports grows from ~27k (Jan 2023) to ~89,993 (Jul 2026); a labelled meter is frequently absent from any given month (e.g. 107/391 present in Jan 2024). Labelled-household coverage by window ≈ 68 (2023) / 159 (2024) / 279 (2025) / 324 (2026). | Aggregate features over many months and all four years rather than any single file; add a rollout-era indicator so early, sparsely-metered periods are distinguishable. |
| `MP ID` had to be confirmed as a stable identifier across monthly exports before cross-month aggregation could be trusted. | Verified stable (same `PLZ` for a given `MP ID` across 2024/25/26); cross-month aggregation keyed on `MP ID` is safe. |
| **③ Label quality (GIGI file)** | |
| GIGI is keyed by subsidy application/project, not by household: 1,192 rows but 878 unique `GP-Nr`, with multiple rows per household. | Aggregate rows to household level before labelling; one `GP-Nr` = one training unit. |
| 25 rows have a blank `GP-Nr`. | Unusable — drop them. |
| `PV = "-"` does **not** mean "no PV"; it marks a row that is about a different asset. Of 311 dash rows: 108 heat-pump, 105 battery, 57 EV-charger installs; only 24 have no other asset. | Never interpret `-` as a negative label; resolve PV status at household level by OR-ing across the household's rows. |
| 206 `GP-Nr` show "conflicting" PV values across their rows. | Not a real conflict — each row describes a different asset. Resolved by the household-level OR aggregation above. |
| At household level only 12 households have no PV row and no asset at all (2 with meter data) — GIGI contains essentially zero usable confirmed PV-negatives. | Abandon standard binary classification; treat the task as Positive–Unlabeled (see block ⑤). |
| 126 rows have a blank `PV` cell (blank ≠ no PV); `PV-Leistung in kWp` is populated for only 191 rows. | Exclude blank-`PV` rows from training rather than treating them as negatives; do not rely on `kWp` presence/absence as a signal. |
| 26 households have a battery but no PV row (10 with meter data); home batteries almost always accompany PV. | Treat battery-but-no-PV households as positives. |
| The labelled set is not a random sample (everyone applied for some subsidised asset) and is ~9:1 skewed toward PV-present — a distribution shift versus the ~90k population. | Do not trust raw class balance; calibrate model output to an externally derived population base rate and report population flag-rate as a sanity check. |
| Many PV commissioning dates fall inside or after the 2023–2026 data window, so a household's pre-install history would be a false-positive label under per-window labelling. | Use whole-record positive labels (one positive row over the full history) plus a change-point feature that captures the pre/post-install transition; no per-household feature windowing. **Scope note:** this holds for the PV MVP (`build_features` → `features_gp.pkl`). The multi-technology property line deliberately does the opposite — `train_property_samples*.csv` windows each sample (`window_anchored_to_install`) and `build_property_aux_windowed.py` recomputes the aux features per window so they differ across a household's before/after pair (7/7 vary; the static version varied in 0/7). Two conventions coexist on purpose; do not mix features across them. |
| **④ Signal and feature extraction** | |
| The feed-in register (OBIS 2.29) nearly solves the task directly (Jan: 50/92 PV vs 2/15 non-PV meters show export; summer near-decisive). | Deliberately **exclude** the feed-in channel from model features — the challenge asks for inference from net load. Use OBIS 2.29 offline only: silver-positive labels, the export-dominant meter-type filter, and evaluation. **Enforced as of `split_feedin_channel.py`:** `train_property_samples*.csv` had violated this, carrying 29 export-derived columns (`einsp_*`, `frac_days_feedin`, `he00`–`he23`, the production-only-meter flags) that separate PV almost perfectly (27.5 vs 12.4 kWh/day mean export). **Train on `train_property_samples_auxw_netload.csv`**; the quarantined columns live in `train_property_samples_auxw_feedin.csv` for offline use only. |
| Consumption-only signal is weak in winter and for high-self-consumption PV systems. | Weight features toward summer months; condition the midday-dip feature on clear-sky days; accept and report an explicit low-confidence band. |
| Confounds in net load: PV homes import less, but so do smaller / better-insulated households; heat pumps raise winter import. | Add control features — night base load (01–04 h) as a household-size proxy and temperature-derived controls for heat-pump load. |
| Weather data (clear-sky days, temperature) is needed but MeteoSwiss stations are sparse relative to postal codes. | MVP uses one canton-AG daily series (mean of the 5 AG stations BEZ/BUS/LEI/MOE/PSI) - radiation barely varies across a canton this size; a per-`PLZ` clear-sky flag from station interpolation is a documented stretch goal. |
| **⑤ No negatives: modelling and evaluation consequences** | |
| With essentially zero confirmed negatives, standard binary classification is impossible. | Positive–Unlabeled (PU) learning: Elkan–Noto (case-control variant) on a `HistGradientBoostingClassifier`. Bagging-PU (Mordelet–Vert) noted as a robustness check, not in the MVP. |
| Silver positives (derived from clear-summer feed-in) are biased toward net-exporting systems, and no silver negatives are defensible (a house with no feed-in may still have self-consuming PV). | Use silver positives only, document the net-exporter bias, and report recall on silver positives separately from GIGI positives. |
| Standard precision/recall and ROC cannot be computed without negatives. | PU-adjusted PR-AUC / ROC-AUC using the estimated label frequency `c`, plus recall on held-out known positives and population flag-rate versus the base rate. |
| No known PV penetration base rate is available for calibration. | Per-postcode rate = BFE ElPA PV plants ≤30 kWp ÷ **metered households in our own population** (one recent export) - the right denominator for this population and no BFS dependency. Canton-AG result ≈ 11%; national reference ~12–14%. |
| The ElPA register undercounts small PV installations without a guarantee of origin. | Treat the derived base rate as a lower bound and sensitivity-test it over ×1.0–1.5. |
| Cross-validation must not let a multi-meter household straddle folds. | **No longer true by construction** for the property tables: `train_property_samples*.csv` holds 342 rows over 335 households, because 7 households contribute both an `augmented_before` and a cross-sectional sample. Group-split on `group_id` (== `gp_nr`); a random split leaks a household across folds. The PV MVP path is still one row per `GP-Nr` and remains safe. |

**Ordering scheme:** rows follow the data pipeline end to end — ① raw files & formats, ② linking households to meters, ③ label quality, ④ signal & feature extraction, ⑤ modelling & evaluation consequences — and within each block the most fundamental or blocking problem is listed first.


## Session update — per-meter auxiliary features (2026-09-10)

Added after the table above was written; see `data_addition/Readme.md` for the
file-level detail.

| Problem | Solution / Decision |
|---|---|
| Aggregating a household's meters to `GP-Nr` hides *which* meter carried the load. 29 households have a **dedicated heat-pump meter** (winter-only, near-zero summer) and 17 a **dedicated PV production point**; summed into a household total, both signals are diluted or invisible. | `build_meter_aux.py` keeps the per-meter monthly view for the 413 labelled meters; `build_property_aux.py` rolls it up into features the aggregate cannot express (`n_meters`, `has_dedicated_hp_meter`, `meter_max_winter_summer_ratio`, `meter_concentration`). The production-only flags are export-derived and therefore quarantined — see block ④. |
| The aux features were initially computed over each meter's whole history, so they were identical across a household's before/after pair — useless for exactly the comparison that pair exists to make. | `build_property_aux_windowed.py` recomputes them per sample window. |
| A first version of the heat-pump flag fired on 64% of households: on a single-meter household "max winter/summer ratio over meters" is just that household's own seasonality, and this subsidy-applicant population is winter-heavy. | Split into `is_winter_dominant` (household seasonality, weak) and `has_dedicated_hp_meter` (multi-meter only: one winter-only meter *beside* a normal one). Prefer the latter, or the continuous ratio. |
| The aux features show almost no separation against `has_Waermepumpe` (0.103 vs 0.081). | **That contrast cannot establish they are useless** — `has_Waermepumpe = 0` is unlabelled, not a verified negative (block ③), so the numbers are a floor, not an accuracy estimate. The valid within-subject contrast on the 10 install-anchored manifest households moves the other way: the seasonality ratio rises after installation in **5 of 6 comparable pairs**. Six pairs proves nothing, but it is the contrast that is not corrupted by unlabelled negatives. |
| A full pass over the exports takes ~17 min, which is expensive to repeat for one month. | `build_meter_aux.py --only YYYY-MM` rescans named months and splices them into the existing output (2024-10 took 13 s). |
| Two derived tables exceed GitHub's 100 MB limit (`load_property_daily.csv` 257 MB, `train_property_sequences.csv` 133 MB). | Git-ignored; regenerate locally from `store/input_data`. Git LFS if they must be tracked. |

**Data is live.** `store/input_data` is a CIFS share that was written to during
the event: the 2023 exports carried an extra `Zählpunktbezeichnung` column
earlier in the day and were rewritten to the standard 4-metadata-column layout
mid-session. Anything derived before 2026-09-10 ~17:00 may have been built
against the older schema. Re-verify column positions after a pull.
